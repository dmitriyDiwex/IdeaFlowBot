# Спецификация эффективной модерации предложек

Статус: проект v1\
Назначение: сократить число MCP-вызовов, объём контекста и время обработки сообщений, сохранив обязательное подтверждение человеком перед применением решений.

## 1. Целевой сценарий

Стандартная команда пользователя:

> Подготовь 100 самых старых сообщений из разрешённых предложек, пропусти медиа и дай решения на подтверждение.

Ожидаемый процесс:

1. MCP одним запросом выбирает 100 самых старых подходящих сообщений.
2. MCP добавляет только компактные признаки: предложка, дата, первые 300 символов, сведения о дубле и релевантные прошлые решения.
3. Агент предлагает решение и короткий код причины для каждой строки.
4. Пользователь подтверждает список или меняет решения по номерам строк.
5. MCP применяет подтверждённые решения, соблюдая лимит не более 20 сообщений в одной предложке за любые 60 секунд.
6. MCP самостоятельно проверяет итоговые статусы и синхронизацию карточек Telegram.

До шага 5 статусы сообщений не изменяются.

## 2. Постоянный профиль выборки

Профиль `student_default_v1`:

- порядок: от самого старого сообщения к новому;
- размер стандартной выборки: 100;
- учитывать статусы `new` и, только по явному запросу, `hold`;
- сообщения, уже обработанные человеком, не изменять;
- медиа по умолчанию пропускать;
- текст для предварительного просмотра ограничивать 300 символами;
- часовой пояс дат: `Europe/Moscow`;
- старые точные дубли в ЮУрГУ с текстом `Когда домой поедешь?` пропускать;
- список исключённых предложек хранить в конфигурации MCP, а не передавать агенту в каждом запросе.

## 3. Постоянная политика решений

### 3.1. Общий принцип

Если сообщение осмысленно, относится к студенческой жизни и не подпадает под правило отклонения или рекламы, предпочтительное решение — `approve`.

Грубый, токсичный или абсурдный юмор сам по себе не является основанием для отклонения. Нельзя путать неприятный тон с опасным содержанием.

### 3.2. Одобрять

- осмысленные вопросы о вузе, учёбе, общежитии и студенческой жизни;
- знакомства, поиск друзей и бытовые обращения к другим студентам;
- шутки, включая грубые и токсичные, если нет разжигания ненависти или реальной угрозы;
- предложения самостоятельно изменить фотографию в студенческом билете;
- небольшие частные услуги без выраженной коммерческой кампании, например разовая недорогая услуга;
- продажу личных вещей, поиск жилья и бытовые предложения, если это не массовая реклама;
- содержательный текст после вводного обращения вроде «админ, опубликуй» — оценивать сам текст, а не вводную фразу.

### 3.3. Отклонять

- разжигание межнациональной или иной групповой ненависти, призывы к опасному насилию;
- сексуальный контент с несовершеннолетними;
- опросы, анкеты, исследования и поиск респондентов;
- бессмысленные фрагменты, случайные наборы слов, букв или эмодзи без понятного сообщения;
- обращения только к администрации: жалоба, просьба удалить, разблокировать, разослать ссылку или ответить, если самостоятельного сообщения для публикации нет;
- нативную рекламу неизвестных Telegram-каналов и групп, если нельзя надёжно понять, что это некоммерческая официальная учебная группа;
- неактуальные объявления, особенно о уже прошедших концертах и мероприятиях;
- более поздние точные или очевидные дубли одного сообщения в той же предложке;
- рекламу запрещённых или явно нежелательных товаров, например вейпов;
- сообщения, отдельно помеченные пользователем на отклонение в текущей партии.

Если оригинал дубля уже одобрен человеком, оставшиеся дубли отклоняются.

### 3.4. Обрабатывать как рекламу

Решение `advertising` применяется к:

- явному предложению купить рекламу или сотрудничать;
- вопросу о стоимости и условиях размещения рекламы;
- коммерческому предложению с прайсом или систематическим продвижением услуги.

Для `advertising` используется только настроенный сервером ответ рекламного менеджера. Агент не сочиняет свой ответ.

### 3.5. Отправлять на ручную проверку

Решение `hold` допустимо, если для безопасной оценки не хватает содержимого медиа или контекста. При стандартной текстовой выборке медиа лучше исключать ещё на стороне MCP.

## 4. Приоритет правил

Правила применяются сверху вниз:

1. ограничения платформы, безопасность и закон;
2. явные изменения пользователя для конкретных строк текущей партии;
3. постоянные правила, которые пользователь сформулировал для всех будущих сообщений;
4. дубли и потеря актуальности;
5. реклама, опросы и обращения к администрации;
6. осмысленность и полезность сообщения;
7. при отсутствии причины для отклонения — `approve`.

Разовое указание вроде «строки 80 и 81 в этот раз одобри» не становится постоянным правилом.

## 5. Компактные коды причин

Агент возвращает код причины, а сервер разворачивает его в человекочитаемую запись журнала:

| Код | Значение |
|---|---|
| `ok` | допустимое осмысленное сообщение |
| `duplicate` | повтор сообщения |
| `survey` | опрос или поиск респондентов |
| `admin_only` | только обращение к администрации |
| `advertising` | запрос или коммерческое размещение рекламы |
| `native_promo` | неясная нативная реклама канала или группы |
| `meaningless` | нет осмысленного содержания |
| `outdated` | объявление потеряло актуальность |
| `hate_or_incite` | групповая ненависть или опасный призыв |
| `targeted_threat` | реальная адресная угроза |
| `minor_sexual` | сексуальный контент с несовершеннолетними |
| `media_review` | требуется просмотр медиа |
| `manual_review` | неоднозначный случай |

В запрос на применение достаточно передавать `row`, `decision` и `reason_code`. Повторно отправлять текст сообщений не нужно.

## 6. Предлагаемый MCP API

### 6.1. `prepare_moderation_batch`

Один вызов заменяет получение списка очередей и отдельное чтение каждой предложки.

Вход:

```json
{
  "profile": "student_default_v1",
  "limit": 100,
  "order": "oldest",
  "media": "exclude",
  "text_limit": 300
}
```

Выход:

```json
{
  "snapshot_id": "stable-id",
  "policy_version": "student_default_v1",
  "selected_count": 100,
  "skipped_media_count": 12,
  "rows": [
    {
      "row": 1,
      "submission_id": "...",
      "channel": "bot_short_code",
      "submitted_at_msk": "2026-10-03 12:34",
      "text_preview": "...",
      "duplicate": null,
      "relevant_history": []
    }
  ]
}
```

Требования:

- фильтрация исключённых предложек выполняется в SQL;
- выборка глобальная, а не по одной предложке;
- сортировка детерминированная: `submitted_at`, затем `submission_id`;
- группировка медиа выполняется до применения `LIMIT`, чтобы партия действительно содержала 100 строк;
- данные канала не повторяются большим объектом в каждой строке;
- имя и другие данные автора по умолчанию не возвращаются;
- точный дубль определяется существующим хешем текста, а вариант с изменённой пунктуацией — нормализованным хешем;
- возвращаются только релевантные прошлые решения, максимум 1–3 на неоднозначную строку; несвязанные примеры не возвращаются;
- `snapshot_id` сохраняет точное соответствие номера строки и сообщения между ходами диалога и после перезапуска агента.

### 6.2. `commit_moderation_batch`

Вход:

```json
{
  "snapshot_id": "stable-id",
  "decisions": [
    {"row": 1, "decision": "approve", "reason_code": "ok"},
    {"row": 2, "decision": "reject", "reason_code": "survey"}
  ],
  "verify_after_apply": true
}
```

Требования:

- вызов допустим только после явного подтверждения пользователя;
- перед изменением проверяется ожидаемый статус из снимка;
- сообщение, уже обработанное человеком, пропускается как конфликт и никогда не перезаписывается;
- повторный вызов с тем же `snapshot_id` идемпотентен;
- сервер сам распределяет действия по предложкам;
- в каждой предложке применяется не более 20 решений за скользящие 60 секунд;
- сервер ожидает освобождения лимита или возвращает сохраняемое задание, которое можно безопасно продолжить;
- после применения сервер проверяет итоговый статус и обновление Telegram-карточки;
- результат возвращается компактной сводкой, а подробности — только для ошибок и конфликтов.

Пример результата:

```json
{
  "requested": 100,
  "applied": 97,
  "conflicts": 2,
  "failed": 1,
  "telegram_sync_warnings": 1,
  "exceptions": []
}
```

### 6.3. `list_pending_summary`

Для вопроса «сколько осталось» нужен отдельный дешёвый вызов, который возвращает:

- общее число необработанных сообщений в разрешённых предложках;
- список предложек по убыванию количества;
- отдельно число исключённых медиа и `hold`, если это запрошено.

Он не должен возвращать тексты сообщений.

## 7. Формат показа пользователю

Перед применением агент показывает только:

| № | Дата МСК | Предложка | Текст, до 300 символов | Решение | Причина |
|---:|---|---|---|---|---|

Для больших партий разрешено делить таблицу на блоки по 25 строк, но нумерация должна оставаться сквозной. Внутренние ID пользователю не показываются.

Ответ пользователя вида:

> 1 и 8 отклони, 14 одобри, остальные как решил

преобразуется в изменения по номерам строк того же `snapshot_id`.

## 8. Хранение черновика

Черновик партии должен храниться на стороне сервера, а не только в памяти агента.

Минимальные поля:

- `snapshot_id`;
- время создания и срок действия;
- версия политики;
- выбранные `submission_id` и ожидаемые статусы;
- исходные предложения агента;
- изменения пользователя;
- состояние: `awaiting_approval`, `applying`, `applied`, `stale`;
- краткий итог применения.

Это предотвращает потерю соответствия номеров после перезапуска MCP, контейнера или диалога.

## 9. Контекстный playbook и его публикация через MCP

### 9.1. Для чего нужен `MODERATION_AGENT_PLAYBOOK.md`

Файл `docs/MODERATION_AGENT_PLAYBOOK.md` — это переносимый контекст накопленного опыта модерации. Он нужен, чтобы новый агент или новый чат не зависел от длинной истории предыдущего диалога и с первой партии понимал:

- общий уклон в пользу публикации осмысленных студенческих сообщений;
- разницу между токсичной шуткой и действительно опасным содержанием;
- правила для опросов, рекламы, небольших частных услуг и нативного продвижения;
- разницу между чистым обращением к администратору и полноценным постом с вводной просьбой;
- обработку дублей, неактуальных событий, медиа и неоднозначных случаев;
- порядок предварительного показа решений, пользовательских поправок и последующего применения;
- операционные ограничения: защита человеческих решений, лимит Telegram и обязательная проверка результата.

Playbook не должен жёстко ограничивать агента и не является неизменяемой политикой. Он задаёт разумные значения по умолчанию, когда пользователь не дал более свежего указания.

Приоритет контекста:

1. системные требования, безопасность платформы и закон;
2. свежие явные указания пользователя в текущем чате;
3. другие относящиеся к задаче указания текущего чата;
4. `MODERATION_AGENT_PLAYBOOK.md`;
5. релевантные исторические примеры и самостоятельная оценка агента.

Если текущая команда пользователя противоречит playbook, применяется текущая команда, если она допустима. Разовые изменения строк не записываются в постоянный playbook автоматически.

Разделение ответственности документов:

| Источник | Назначение |
|---|---|
| `AGENT_MODERATION_OPTIMIZATION_SPEC.md` | архитектура MCP, форматы инструментов, производительность и гарантии применения |
| `MODERATION_AGENT_PLAYBOOK.md` | смысловые предпочтения, опыт принятия решений, пограничные случаи и примеры |
| текущий чат | актуальная задача, временные исключения и пользовательские изменения решений |
| база IdeaFlow | живые сообщения, статусы, решения людей, снимки партий и аудит |

### 9.2. Почему playbook следует отдавать через MCP

Если файл доступен только в локальном репозитории, агент в другом чате или клиенте может его не обнаружить. MCP должен предоставлять одну актуальную версию playbook рядом с инструментами модерации.

При этом полный текст нельзя добавлять:

- в описание каждого MCP-инструмента;
- в каждый результат `list_pending_submissions` или `prepare_moderation_batch`;
- в каждую строку партии;
- в системные инструкции сервера целиком.

Иначе одинаковый контекст будет многократно расходовать токены. Агент должен загрузить playbook один раз на новый чат и повторно читать его только при изменении версии или по явному запросу пользователя.

### 9.3. Основной MCP resource

MCP публикует read-only resource:

```text
ideaflow://moderation/playbook/current
```

Предлагаемые метаданные:

```json
{
  "uri": "ideaflow://moderation/playbook/current",
  "name": "IdeaFlow moderation playbook",
  "description": "Мягкие значения по умолчанию и примеры для модерации предложек. Указания пользователя в текущем чате имеют приоритет.",
  "mimeType": "text/markdown"
}
```

Содержимое resource берётся из `docs/MODERATION_AGENT_PLAYBOOK.md`. Не следует поддерживать вторую вручную скопированную версию текста внутри `server.py`, иначе версии начнут расходиться.

Дополнительно можно опубликовать неизменяемый адрес конкретной версии:

```text
ideaflow://moderation/playbook/1.0.0
```

`current` указывает на последнюю развёрнутую версию, а версионный URI позволяет воспроизвести старое решение при аудите.

### 9.4. Короткая инструкция сервера

В общих инструкциях MCP достаточно одной короткой директивы:

> Перед первой обработкой предложек в новом чате загрузите `ideaflow://moderation/playbook/current`. Используйте его как мягкий контекст; свежие указания пользователя важнее. Не загружайте повторно, если `policy_version` не изменился.

Полный playbook в инструкции сервера не встраивается.

### 9.5. Версия и контроль изменений

Сервер при запуске извлекает из файла или конфигурации:

- `policy_version`;
- дату обновления;
- SHA-256 содержимого;
- URI текущей и точной версии.

Каждый связанный ответ MCP возвращает компактный объект:

```json
{
  "policy": {
    "version": "1.0.0",
    "sha256": "...",
    "resource_uri": "ideaflow://moderation/playbook/current"
  }
}
```

Текст playbook при этом не повторяется.

Если агент уже загрузил ту же версию или тот же SHA-256 в текущем чате, повторное чтение не требуется. Если версия изменилась между подготовкой и применением партии, сервер не должен молча пересчитывать решения: снимок сохраняет исходную `policy_version`, а изменение показывается как предупреждение.

### 9.6. Сценарий загрузки в новом чате

```text
Пользователь просит модерировать сообщения
        ↓
Агент получает описание инструментов IdeaFlow MCP
        ↓
Агент один раз читает ideaflow://moderation/playbook/current
        ↓
Агент запоминает policy_version в контексте чата
        ↓
prepare_moderation_batch возвращает сообщения и ту же policy_version
        ↓
Агент предлагает решения, применяя указания текущего чата поверх playbook
        ↓
Пользователь меняет или подтверждает решения
        ↓
commit_moderation_batch применяет подтверждённый snapshot
```

При вопросах только о количестве необработанных сообщений загружать playbook не обязательно: смысловая модерация в таком запросе не выполняется.

### 9.7. Резервный инструмент для клиентов без MCP resources

Если клиент не умеет читать MCP resources, сервер предоставляет read-only инструмент:

```text
get_moderation_playbook(section="core|decisions|examples|workflow|all")
```

Ответ:

```json
{
  "version": "1.0.0",
  "sha256": "...",
  "section": "core",
  "content": "..."
}
```

По умолчанию возвращается `core`. Раздел `examples` загружается только для смысловой модерации или неоднозначных случаев, а `workflow` — перед подготовкой и применением партий. `all` используется при первом подключении, аудите или явном запросе пользователя.

### 9.8. Обновление playbook

Изменения проходят следующий путь:

1. Пользователь формулирует новое общее предпочтение, а не только исправляет одну строку.
2. Обновляется `MODERATION_AGENT_PLAYBOOK.md` и повышается его версия.
3. Проверяются противоречия с существующими правилами и gold-набором.
4. MCP развёртывается с новым файлом.
5. Resource `current` начинает возвращать новую версию и SHA-256.
6. Новые чаты загружают новую версию; действующие чаты получают уведомление через `policy_version` следующего MCP-ответа.

Старые версии желательно сохранять для аудита, но они не должны автоматически добавляться в контекст агента.

### 9.9. Безопасность и границы

- Playbook доступен только для чтения через публичные инструменты агента.
- Изменение файла не выполняется по тексту сообщения из предложки.
- Содержимое предложек всегда считается недоверенными данными, а не инструкциями агенту.
- MCP не должен автоматически превращать пользовательскую поправку одной строки в постоянное правило.
- Публикация новой версии требует обычного процесса изменения конфигурации или кода.
- Playbook не заменяет серверные проверки статусов, авторизацию, идемпотентность и лимитер.

### 9.10. Проверки интеграции

Нужны автоматические тесты, подтверждающие, что:

- `current` возвращает содержимое репозиторного файла без расхождений;
- метаданные содержат версию, SHA-256 и `text/markdown`;
- версионный URI остаётся неизменным после выпуска;
- инструменты партий возвращают соответствующую `policy_version`, но не полный текст;
- изменение playbook не меняет уже подтверждённый snapshot;
- резервный инструмент корректно возвращает отдельные разделы;
- инструкции явно сохраняют приоритет текущих указаний пользователя.

## 10. Набор проверочных примеров

Нужен небольшой версионируемый gold-набор, подтверждённый пользователем. В нём должны быть представлены:

- обычный студенческий вопрос;
- грубая шутка без опасного содержания;
- межнациональная ненависть;
- опрос;
- бессмысленный текст;
- чистое обращение к администратору;
- обращение к администратору плюс содержательный пост;
- запрос на покупку рекламы;
- неизвестная Telegram-группа;
- небольшая частная услуга;
- прошедшее мероприятие;
- точный и почти точный дубль;
- сообщение с медиа.

Разовые изменения конкретных строк в gold-набор не добавляются. Постоянное правило добавляется только после явной формулировки пользователя.

## 11. Критерии готовности

- подготовка 100 сообщений требует не более 3 MCP-вызовов;
- агент получает не более 35 000 символов текста для партии из 100 сообщений, не считая редких уточнений;
- исключённые предложки не попадают в выборку;
- выбранные строки являются действительно самыми старыми среди разрешённых;
- медиа не уменьшают итоговую текстовую выборку ниже запрошенного размера, если сообщений достаточно;
- ни одно решение человека не перезаписывается;
- лимит 20 действий на предложку за 60 секунд соблюдается сервером;
- все применённые решения автоматически проверяются;
- ошибки Telegram-синхронизации видны в итоговой сводке;
- повторный запуск одного подтверждённого снимка не создаёт повторных действий;
- пользователь может изменить решения по номерам строк без передачи внутренних ID.
- новый чат может получить актуальный `MODERATION_AGENT_PLAYBOOK.md` через один MCP resource;
- полный playbook не дублируется в результатах рабочих инструментов;
- каждый снимок партии хранит версию смысловой политики, с которой он был подготовлен.

## 12. Приоритет внедрения

1. Опубликовать `MODERATION_AGENT_PLAYBOOK.md` как read-only MCP resource с версией и SHA-256.
2. Добавить серверный профиль исключений и `list_pending_summary`.
3. Реализовать `prepare_moderation_batch` с глобальной SQL-выборкой, `snapshot_id` и `policy_version`.
4. Добавить компактные коды причин и метаданные дублей.
5. Реализовать `commit_moderation_batch` с серверным лимитером и проверкой результата.
6. Создать gold-набор и автоматические проверки политики.
7. После стабилизации API оформить короткий специализированный навык Codex, который будет только маршрутизировать эти два шага и загружать playbook по MCP.
